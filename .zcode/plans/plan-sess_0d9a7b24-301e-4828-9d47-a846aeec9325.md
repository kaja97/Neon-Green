# Neon Farming — Full Backend + Frontend Fix Plan

## Analysis summary

I read all docs (`doc/`, `.agents/`, `Project plan/`) and the entire backend + frontend. The core flows the request names — **farmer account edit, project, activity, disease add + solve method** — are blocked by real bugs, not just missing UI. There are two systemic defect classes plus several missing features.

## Two systemic bug classes (these break the app end-to-end)

### BUG 1 — Ownership checks compare the wrong ID (Critical)
`Project.farmer_id` stores **`FarmerProfile.id`**, but `get_current_user` returns an **`Account`** whose `.id` is the `Account.id`. Five services compare `project.farmer_id != account_id` directly, so every legitimate owner gets a **404**. The correct pattern already exists in `project/service.py` (`_get_farmer_profile`) and `notification/service.py` (`_get_farmer_id`).

Affected files:
- `backend/modules/disease/service.py` — lines 14, 35, 87 (report_issue, get_issues, resolve_issue)
- `backend/modules/planner/service.py` — lines 17, 27 (get_activity, get_active_plan)
- `backend/modules/soil/service.py` — lines 15, 51, 76 (submit, get_tests, get_recommendations)
- `backend/modules/weather/service.py` — lines 18, 127 (get_weather, get_alerts)
- `backend/modules/admin/service.py` — line 87 (get_user_detail project count → always 0)

**Fix:** add a shared `_get_farmer_id(db, account_id)` helper (resolve Account→FarmerProfile) to each service and compare against that. Reuse the existing `notification` helper pattern.

### BUG 2 — Inconsistent response envelope (Critical)
Half the routers wrap responses in `{success, data, meta}` via `success_response()`; the other half (`weather`, `ai`, `soil`, `planner`, `disease`, `market`) return **raw** data. The frontend reads inconsistently: `useWeather.ts`/`useAISummary.ts` read `res.data.data` (→ **undefined**, page breaks), while the weather/disease pages read `res.data` directly. This is why pages "don't work with frontend".

**Fix (chosen): standardize on the wrapped envelope everywhere** — it's the documented contract (`core/response.py` + `.agents/backend-rules.md`). Convert the 6 unwrapped routers (weather, ai, soil, planner, disease, market) to use `success_response()`/`paginated_response()`, removing their `response_model=` declarations. This makes the frontend's `res.data.data` pattern correct and consistent across the app.

## Backend feature fixes & additions

### A. Weather crash — `location.latitude`/`location.longitude` don't exist
`FarmerLocation` stores a PostGIS `centroid`, not lat/lon columns. `weather/service.py:38` crashes.
**Fix:** extract via `to_shape(location.centroid)` → `.y`/`.x` (same pattern as `farmer/schemas.py`).

### B. Activity manual CRUD (new — per your decision to add it)
Currently planner = read + complete + skip only. Add manual task management alongside AI tasks.
- `planner/schemas.py`: add `ActivityCreate` (title, activity_type, description, due_date) and `ActivityUpdate`.
- `planner/service.py`: add `create_activity`, `update_activity`, `delete_activity` — each verifies project ownership via the fixed helper and writes to the project's **active** `ActivityPlan` (creates the plan row if none exists), flags manual tasks with `is_ai_recommended=False`.
- `planner/router.py`: add `POST /planner/{project_id}/activities`, `PUT/PATCH /planner/activities/{id}`, `DELETE /planner/activities/{id}`.
- Also fix the skip field-name mismatch: frontend sends `reason`, backend `SkipRequest` expects `skipped_reason`. I'll accept both (alias) so neither side breaks.

### C. Disease "add + solve method" (the key requested flow)
Currently you can *report* an issue and *search* the disease library, but there's **no way to add a disease with its solutions** and no UI to view solutions — the "View Treatments" link is a dead `href="#"`.

Backend additions:
- `disease/schemas.py`: add `DiseaseSolutionCreate`, `DiseaseSolutionResponse` already exists.
- `disease/service.py`: add `list_all_diseases` (for admin library browse — empty `q` returns all), `create_disease_with_solutions` / `update` / `delete` that accept plant_id (fixes the NOT NULL FK bug below) and a nested `solutions[]` array.
- `disease/router.py`: add `GET /disease` (list all, for library browse), `GET /disease/{disease_id}/solutions` already exists (keep), admin create/update/delete go through admin router.

Fix the admin `DiseaseCreate` schema bug: `plant_diseases.plant_id` is NOT NULL but `DiseaseCreate` omits it → DB error. **Add `plant_id` to `DiseaseCreate`/`DiseaseUpdate`** and the nested solutions, and create solutions from the same payload.

### D. `IssueResponse` missing `resolved_date`
Service sets `issue.resolved_date` but the response model omits it → the field is dropped. Add it to the schema.

### E. Soil detail serialization
`get_soil_tests` attaches `results`/`recommendations` to the ORM object but `SoilTestResponse` has no such fields, so they're stripped. Switch the list endpoint to `SoilTestDetailResponse` so the latest test carries its nutrient results + recommendations.

### F. Add admin `/diseases` (list all) endpoint + list endpoint fixes
Admin master-data page currently abuses `/disease/search?q=` to list diseases. Add a proper `GET /admin/diseases` list endpoint (and `GET /admin/plants` list) so the library pages have a real source.
