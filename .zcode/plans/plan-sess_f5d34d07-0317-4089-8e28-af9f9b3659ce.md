# Neon Farming — Bug Fix & Feature Plan

Scope: 7 issues across frontend (Next.js/React/Tailwind) + backend (FastAPI/SQLAlchemy). Sequenced **Phase 1 (4 bugs) → Phase 2 (3 features)**, per your choice. All activity types use an **enum list** (not a table), profile/settings stay **merged as Account Hub**, fertilizer tracking reuses the existing **ActivityDetail** table (no new tables), and all new strings stay inline (no new translation keys).

## PHASE 1 — Bugs

### 1. Modal scroll (bottom hidden / can't scroll)
**Root cause:** `Modal.tsx` centers with `top-1/2 -translate-y-1/2` + `max-h-[90vh]`. When content is tall, the translate pushes the top edge above the viewport and the inner `overflow-y-auto` can't be reached.

**Fix** — `frontend/components/ui/Modal.tsx`:
- Replace centering transform with a flex overlay that scrolls: outer wrapper `fixed inset-0 z-50 overflow-y-auto flex items-start md:items-center justify-center p-4` (so the whole viewport scrolls and the modal stays reachable on small screens).
- Keep the panel `max-h-[90vh]` + inner `overflow-y-auto`, but add a top safe-area so it never sits under the TopBar on mobile.
- One file, ~10 lines. Fixes the "Add Task / Edit / Complete Activity" modal and the Edit Project modal.

### 2. Activity-type enum mismatch (the planner's tasks never match the UI → no water/fertilizer capture; "Other" has no name)
**Root cause:** Planner engine emits `watering` / `fertilizing` / `monitoring`; frontend uses `irrigation` / `fertilizer` / `pest_control` / etc. They never align, so the "Complete Activity" modal never shows the water/fertilizer inputs.

**Fix — standardize to a single enum list:**
`irrigation, fertilizer, pest_control, disease_check, harvesting, weeding, soil_preparation, monitoring, other`

- **Backend:**
  - Add `ACTIVITY_TYPES` list + a normalizer in `backend/modules/planner/schemas.py`.
  - Map engine output in `engine.py`: `watering→irrigation`, `fertilizing→fertilizer`, `monitoring→monitoring`.
  - `ActivityCreate`: validate `activity_type` against the enum.
  - Accept an optional **`name`** field on `ActivityCreate`/`ActivityUpdate`/`FarmingActivity` for the "Other" custom title (store in the existing `title`; the type stays `other`). No migration needed for this — `title` already exists.
- **Frontend:** Update the `ACTIVITY_TYPES` array in `plan/page.tsx` to the same enum; show an extra "Custom name" input when type = `other`. Add `weeding`, `soil_preparation`, `monitoring` to the select.

### 3. Profile/Settings same page
**Root cause:** `/settings/page.tsx` just `router.replace('/profile')`; BottomNav/TopBar only link `/profile`.

**Fix:** Delete `frontend/app/(app)/settings/` route entirely (removes the duplicate URL). Update any remaining `href="/settings"` references to `/profile` (none found in layout/TopBar/BottomNav, so this is mostly cleanup). One clear Account Hub URL.

### 4. Dashboard tiles empty (soil/plan/disease/market show defaults)
**Root cause:** `backend/modules/project/dashboard.py::get_dashboard` never populates `soil_status` / `market_price`. `weather`/`ai_summary` also untouched. Disease is driven by `active_issues` (already populated) — that one is fine; the visible "0 issues" is correct when none exist.

**Fix — wire the aggregator to read existing services (all already take `account_id`):**
In `dashboard.py`, add a parallel gather block that:
- **soil_status** → call `soil.service.get_soil_tests(db, project_id, account_id)`; if any, map `tests[0]` to `{ph: results.ph_level, nitrogen_status: results.nitrogen_level, last_test: test_date.isoformat()}`. Wrap in try/except → `None` on failure.
- **market_price** → `market.service.get_trend(db, project.plant_id)` → map to `{price_per_kg: current_price, trend: direction, change_pct: change_percentage}`. try/except → `None` (e.g. no market data seeded).
- **weather** (read-only, used by tiles/cards) → call once, map `current` fields. try/except → `None`.
- **ai_summary** → **read the stored `AIProjectSummary` row directly** (do NOT call `get_project_summary`, which is rate-limited and writes on every call). Map `summary_json` + `last_updated_at` to `{text, generated_at, source}`.

All four are wrapped individually so one failing source doesn't blank the dashboard. This is the same pattern already used for the existing gather block.

## PHASE 2 — Features

### 5. Crop-day activity context on Plan page
**Goal:** "based on days passed planted, show what to do that day." The engine already generates per-day activities from crop data; the plan page currently shows a flat list.

**Implementation:** On `plan/page.tsx`, add a **"Today" highlight card** at the top using `dashboard.farming_circle` (current_day, total_days, current_stage name + watch_for/critical_actions) and filter activities whose `planned_date == today`. Surface the stage's `watch_for` / `critical_actions` (already on `PlantStage`) so the farmer sees crop-specific guidance. The data already exists — this is presentation only (frontend).

### 6. Farm Q&A on project page
**Goal:** "option for farmer to ask questions, then based on crop data" — the AI chat already loads crop context server-side.

**Implementation:** Add a compact **"Ask about your farm"** input on the project dashboard (`projects/[id]/page.tsx`) that POSTs to the existing `/ai/{project_id}/chat` endpoint and shows the inline answer, with a "Continue in chat" link to `/projects/{id}/ai`. Reuses `AIChatWindow` patterns + existing endpoint. Frontend-only addition (one new small block component).

### 7. Project page: weather card + fertilizer log card
**Goal:** "show weather data, new fertilizer add date, fertilizer details."

**Implementation:**
- **Weather card:** replace the tiny WeatherBlock-on-dark-bg with a proper card on the project page showing current temp/condition/rain/humidity + a 5-day mini-forecast (data now present in `dashboard.weather` after P1#4, or via the existing `/weather/{id}` endpoint). 
- **Fertilizer log card:** new component reading activities where `activity_type == "fertilizer"` (completed or pending) for the project, showing last application date + name + qty (from `ActivityDetail.actual_fertilizer_kg` / `title`). "Log application" opens the existing Add-Task modal pre-set to type `fertilizer`. No new table — reuses `FarmingActivity` + `ActivityDetail`.
